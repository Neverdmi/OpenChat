# OpenChat — спецификация v1

Анонимный текстовый мессенджер на публичной инфраструктуре.
Рабочее имя проекта — `OpenChat` (легко переименовать), префикс протокола — `openchat/`.

---

## 0. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Tor | Три режима: `off`, `fallback` (прямое соединение, при ошибке — через Tor), `always` (весь трафик через Tor SOCKS5, fail-closed). Реализация: встроенный `arti-client` (чистый Rust, без внешнего бинарника) + SOCKS5-сервер поверх него в `oc-tui`; транспорт ходит через SOCKS. `.onion`-хосты проходят через SOCKS5 как есть (Tor резолвит их сам). |
| Платформы | Linux `x86_64-unknown-linux-gnu` (glibc), `x86_64-unknown-linux-musl` (статика, работает и на glibc), `aarch64-unknown-linux-gnu`; Windows `x86_64-pc-windows-msvc` — проверить позже. macOS — позже. |
| Релеи | Встроенный курируемый пул по умолчанию + возможность добавлять/удалять свои. В репозитории есть `oc-relay` — self-hosted релей без логов, чтобы любой мог поднять свой. |
| PQ | Гибрид `X25519 + ML-KEM-768` с v1. Формат ключей/инвайтов сразу PQ-совместимый, fallback на чистый X25519 только для совместимости со старыми клиентами. |
| Файлы | Не поддерживаются. Только текст (и служебные кадры). |

## 1. Цели и не-цели

### Цели
- Контент не может расшифровать ни релей, ни сетевой наблюдатель.
- Личность отправителя скрыта от релея (sealed sender).
- Сообщения нельзя связать между собой по адресам на релее.
- Устойчивость к блокировкам: несколько независимых типов носителей и большой пул релеев.
- Нулевая регистрация: только invite-ссылка/QR.
- Любой человек может пользоваться без своего сервера.

### Не-цели
- Защита от глобального пассивного наблюдателя (это уровень микширования/Tor).
- Скрытие IP от релея без Tor (честно фиксируем: IP виден релею).
- Защита от компрометации конечного устройства.
- Групповые чаты в v1 (задел под MLS есть, реализация позже).
- Передача файлов, звонки, медиа.

## 2. Модель угроз

| Противник | Возможности | Что обязан не смочь |
|---|---|---|
| Пассивный DPI | видит TLS/WebSocket, размеры, тайминги | определить протокол, прочитать контент, восстановить структуру переписки |
| Активный MITM | подменяет сигналинг/SDP/релей | вклиниться в handshake, подменить ключи |
| Недоверенный релей | читает, хранит, логирует события | расшифровать контент, связать отправителя с получателем, связать сообщения |
| Компрометация долгосрочного ключа | получает identity-ключ | расшифровать прошлые сообщения (FS), подделать старые сообщения |
| Блокировщик | режет домены/IP/протоколы | полностью отрезать пользователя (цена блокировки должна быть выше, чем у легитимных сервисов) |

## 3. Идентичность и приглашение

### Ключи
- `IK_sign` — Ed25519, долгосрочная подпись.
- `IK_dh` — X25519, долгосрочный DH.
- `SPK` — X25519 signed prekey, ротация раз в 7 дней.
- `PQK` — ML-KEM-768 encapsulation key, ротация раз в 7 дней.
- `PeerID = BLAKE2b-256("openchat/peer-id/v1" || IK_sign_pub)`.

### Bundle (публикуется в invite)
```
version(1) | IK_sign(32) | IK_dh(32) | SPK(32) | created_at(8)
           | pq_len(2) | PQK(1184) | signature(64)
```
`signature = Ed25519(IK_sign, "openchat/bundle/v1" || всё выше)`.

### Invite
```
openchat://v1/<peer_id_b32>[/<relay_hints_b64>]                        (короткая)
openchat://v1/<peer_id_b32>/<bundle_b64>[/<relay_hints_b64>]          (полная)
```
- Короткая форма (по умолчанию, ~70 символов): только peer id; bundle
  забирается с bundle-mailbox (раздел 4.2).
- Полная форма: bundle встроен в ссылку (~1.9 КБ, в основном из-за
  ML-KEM-ключа); нужна, когда bundle нельзя забрать с релеев
  (например, релей недоступен). Принимается для совместимости.
- `peer_id_b32` — PeerID без padding, base32 (uppercase).
- `bundle_b64` — bundle из раздела выше, base64url без padding.
- `relay_hints_b64` — необязательный сегмент: base64url от списка URL,
  разделённых `\n`; максимум 16 подсказок. Встроенные дефолтные релеи
  в hints не включаются (они уже есть у каждого клиента) — только
  пользовательские, чтобы ссылка оставалась короче.
- Если сегмент отсутствует или пуст, используются только локальные релеи.
- Передаётся вне канала (QR, текст, любой мессенджер).
- TOFU + «safety number»: стороны сортируются по `IK_sign`, затем
  `SN = BLAKE2b("openchat/safety/v1" || IK_sign_first || IK_sign_second || IK_dh_first || IK_dh_second)`
  (сортировка парная: порядок dh следует за порядком ed).
- Клиент пинит `IK_sign`/`IK_dh` собеседника при первом добавлении;
  смена identity-ключей у подтверждённого контакта — ошибка, а не тихая
  замена.
- Инициатор подтверждён подписью bundle. Ответчик помечает контакт
  `verified = false`, пока не расшифрует первое ratchet-сообщение: это
  доказывает владение identity-ключом и защищает от подмены/блокировки
  контакта поддельным initiation. Неподтверждённый контакт может быть
  заменён новым рукопожатием; подтверждённый — только ошибкой TOFU.

## 4. Handshake (X3DH-гибрид)

Инициатор A, ответчик B, у A есть bundle B.

```
DH1 = X25519(IK_dh_A, SPK_B)
DH2 = X25519(EK_A,   IK_dh_B)
DH3 = X25519(EK_A,   SPK_B)
PQ  = ML-KEM-768.Encaps(PQK_B)

SK  = HKDF-SHA256(
        salt = 0^32,
        ikm  = DH1 || DH2 || DH3 || PQ_ss,
        info = "openchat/x3dh/v1" || IK_sign_A || IK_sign_B,
        len  = 32)
```
Первый кадр: `Initiation { IK_sign_A, IK_dh_A, EK_A, PQ_ct }`.
B вычисляет те же DH и деинкапсулирует `PQ_ct`.

Свойства:
- Аутентификация A — через DH1 (только владелец `IK_dh_A`), B — через `SPK_B`.
- Гибрид: запись трафика сейчас не даёт расшифровки после появления квантового компьютера.
- AD (associated data) для всех последующих кадров:
  `transcript = "openchat/transcript/v1" || IK_sign_A || IK_dh_A || IK_sign_B || IK_dh_B || EK_A || PQ_ct_len(4 LE) || PQ_ct`.

После handshake:
```
mailbox_root = HKDF(SK, "openchat/mailbox-root/v1", 32)
ratchet_root = HKDF(SK, "openchat/ratchet-root/v1", 32)
```

### 4.1 Доставка Initiation
У ответчика ещё нет сессии, поэтому первый кадр нельзя адресовать на
одноразовый ящик. Initiation публикуется на **handshake-mailbox** —
публичный ключ `SPK_B` из bundle:

```
initiation_padded = frame::pad(Initiation::to_bytes())
inner             = version(1) || kind=1 || initiation_padded
wire              = seal(SPK_B, inner)
mailbox           = SPK_B
```

- `SPK_B` — X25519 signed prekey; его секрет есть только у ответчика.
- Initiation содержит только публичные значения, но внешний конверт всё
  равно запечатан: релей и DPI не видят структуру рукопожатия.
- Ответчик подписывается на `SPK_B` и добавляет контакт после успешного
  `respond`.
- Адрес живёт до ротации prekey (7 дней). При ротации клиент сохраняет
  до двух предыдущих пар `SPK`/`PQK` и продолжает слушать их handshake-
  ящики, поэтому выданные ранее invite-ссылки работают ещё 7–14 дней.
  Одноразовые handshake-ящики появятся вместе с one-time prekeys.
- Повторный Initiation с тем же transcript игнорируется; новый transcript
  заменяет сессию (пересоздание рукопожатия).

### 4.2 Bundle-mailbox (короткие invite)

Короткий invite не несёт bundle, поэтому владелец публикует подписанный
bundle на **bundle-mailbox**, адрес которого выводится из peer id
(публичный вход, поэтому адрес вычислим без секретов):

```
bundle_secret = HKDF-SHA256(salt="", ikm=PeerID, info="openchat/bundle-mailbox/v1", 32)
bundle_mailbox = X25519_base(bundle_secret)
wire           = seal(bundle_mailbox, bundle_bytes)
```

- Клиент публикует bundle при каждом `listen` (троттлинг 5 минут на
  сессию) и **по запросу**: инициатор сначала шлёт sealed
  `bundle_request` на bundle-mailbox собеседника, владелец отвечает
  немедленной публикацией bundle. На store-and-forward релеях
  событие живёт по TTL, на live-only носителях (MQTT) владелец должен
  быть онлайн.
- Инициатор с коротким invite шлёт запрос, подписывается на
  bundle-mailbox и ждёт событие (тайм-авт ~15 c), затем проверяет
  подпись bundle и совпадение peer id — подменить bundle без
  identity-ключа нельзя. Если bundle забрать не удалось, ошибка
  честно говорит, что пир должен быть онлайн (или нужен полный invite).
- Публикация bundle не раскрывает ничего сверх того, что уже есть
  в полном invite (bundle подписан и публичен по дизайну).

## 5. Double Ratchet

Стандартная схема Signal (KDF_RK / KDF_CK), AEAD — XChaCha20-Poly1305.

- На сообщение: заголовок `(dh_pub, pn, n)` + AEAD с AD =
  `transcript || "openchat/ratchet/v1" || header`.
- Пропущенные ключи хранятся ограниченно (≤ 1000) и с TTL.
- Каждый ответ делает DH-ratchet (пост-компрометационная стойкость).
- Никаких подписей на сообщениях — денайябилити.
- Реализуется по спецификации Signal; тест-векторы обязательны.
- Группы позже — MLS (RFC 9420).

## 6. Адресация: одноразовые «ящики»

Релей не должен видеть стабильный pubkey получателя.

```
epoch      = floor(unix_time / 86400)         // сутки
inbox_seed(owner, peer) =
    HKDF(mailbox_root, "openchat/inbox/v1" || owner_pub || peer_pub)
slot_secret(epoch, i) =
    HKDF(inbox_seed, "openchat/slot/v1" || epoch_le || i_le)
mailbox_pk(epoch, i) = X25519_base(slot_secret)
```
- По умолчанию 32 слота на эпоху (`SLOTS_PER_EPOCH = 32`).
- Получатель подписывается на 32 адреса текущей и следующей эпохи, плюс
  на свой handshake-mailbox (`SPK`).
- Отправитель берёт случайный неиспользованный слот (`slot_mask` в
  состоянии); после 32 сообщений маска сбрасывается.
- Подписка мультиплексируется в одном WebSocket через
  `{"type":"subscribe","mailboxes":[...],"since":...}`, поэтому 64+ адресов
  не требуют 64 соединений.
- Через сутки адреса полностью меняются → межсуточная связь невозможна.
- Внутри суток сообщения лежат на разных ключах; связать их можно только по таймингу/размеру, что маскируется паддингом и задержками.

## 7. Sealed sender

Внешний конверт не содержит подписи и личности отправителя.

```
eph        = X25519 ephemeral
shared     = X25519(eph_sk, mailbox_pk)
key        = HKDF(shared, "openchat/seal/v1" || eph_pub || mailbox_pk, 32)
nonce      = random 24
AAD        = "openchat/seal/v1" || eph_pub || mailbox_pk
ciphertext = XChaCha20-Poly1305(key, nonce, AAD, ratchet_ciphertext)

wire = version(1) || eph_pub(32) || nonce(24) || ciphertext
```
Аутентичность содержимого обеспечивает ratchet-AEAD: подделать внутренний шифротекст без ключей сессии нельзя.

## 8. Формат кадра

Внутренний plaintext (до ratchet-AEAD):

```
version(1) | type(1) | flags(1) | reserved(1)
| msg_id(16) | timestamp_ms(8) | body_len(2) | body(body_len)
```
Типы: `TEXT=1`, `ACK=2`, `PING=3`, `REKEY=4`, `COVER=5`.

Паддинг до фиксированных бакетов: **256 / 1024 / 4096 / 16384** байт.
```
frame = len_le(2) || payload || random_padding
```
`len` и padding входят в AEAD, наружу не утекают.

Текст ограничен 4096 байтами UTF-8 (body). Больше — несколько кадров с `msg_id`-цепочкой.

`ACK` (`type=2`) использует тот же заголовок, а тело — 16 байт
`acked_msg_id`. Кадр шифруется обычным ratchet-сообщением после успешной
расшифровки входящего текста. ACK не является подтверждением доставки
релеем: он доказывает, что получатель расшифровал сообщение.

### 8.1 Внутренний конверт клиента
Перед запечатыванием в mailbox:
```
version(1) || kind(1) || payload
kind=1  handshake: payload = frame::pad(Initiation)
kind=2  text:      payload = header(40) || ratchet_ciphertext
```
`ratchet_ciphertext = nonce(24) || AEAD(frame_padded)`. Длина `kind=2`
фиксирована бакетами, `kind=1` — бакетом 4096 из-за ML-KEM ciphertext.

## 9. Транспорт

### 9.1 Носители (приоритет)

| # | Носитель | Роль |
|---|---|---|
| 1 | Свои/курируемые релеи (WebSocket/TLS 443) | основной; текст маленький, store-and-forward идеален |
| 2 | Публичные релеи, добавленные пользователем | расширение пула |
| 3 | WebRTC DataChannel через публичный STUN | P2P, когда оба онлайн; релей не видит трафик; opt-in (см. §9.5) |
| 4 | Публичные MQTT-брокеры (WSS) | другой пул доменов/ASN, камуфляж под IoT |
| 5 | XMPP / Matrix (WSS) | третья экосистема |
| 6 | Tor (`arti`) | `fallback` или `always`; `.onion`-релеи |

### 9.4 MQTT-носитель (WSS)

Второй носитель для обхода блокировок по протоколу/домену (реализован в
`oc-transport` как `MqttClient`, MQTT 3.1.1 поверх WebSocket):

- Эндпоинт задаётся схемой `mqtts://` (или `mqtt://`), транслируется в
  `wss://` (или `ws://`); путь — WebSocket-путь брокера, по умолчанию
  `/mqtt` (явный `/` сохраняется). Схема `mqtttls://` — MQTT поверх
  нативного TLS TCP (обычно 8883) без WebSocket-обёртки. Опционально —
  `user:pass@` из URL.
- Один ящик = топик `openchat/v1/<mailbox_hex>`. Один `RelayEvent` =
  один `PUBLISH` с тем же JSON-пейлоадом, что и у WebSocket-релея.
- QoS 1 в обе стороны; дубли гасятся дедупом по `msg_id` (как при
  нескольких релеях). Retained-сообщений, will и persistent session нет —
  после закрытия соединения брокер ничего не хранит.
- `since` не поддерживается: публичные брокеры не ведут анонимного
  журнала пересылки на ящик, поэтому MQTT — только live-доставка, а
  офлайн-отправку обеспечивает outbox клиента. Публикацию можно делать
  только на брокер, где разрешён анонимный доступ и топики такого вида.

### 9.5 WebRTC-носитель (opt-in)

Прямой P2P-канал между двумя онлайн-клиентами поверх WebRTC
DataChannel (`webrtc-rs`, STUN `stun.l.google.com:19302`):

- Сигналинг (SDP offer/answer, ICE-кандидаты) идёт через обычные релеи
  на **signaling-mailbox** (`HKDF(peer_id, "openchat/webrtc-signaling/v1")`,
  sealed, отправитель внутри сообщения). Сигналинг — live-only, как MQTT.
- После открытия канала зашифрованные payload'ы ящиков идут напрямую
  P2P в обход релеев; релей видит только сигналинг. Нет канала —
  fallback на пул релеев.
- Включается пунктом настроек «WebRTC direct delivery» (по умолчанию
  выкл.). Честные компромиссы: нужны оба онлайн одновременно;
  ICE показывает публичный IP собеседнику и STUN-серверам (релей его
  не видит); с Tor не сочетается (нужен прямой UDP).

### 9.2 Политика выбора
- Отправка: 3–5 случайных релеев из активного пула, успех при ≥1.
- Health-check: latency, uptime, TLS-ошибки; мёртвые/заблокированные временно исключаются.
- Диверсификация пула по ASN/стране/CDN/провайдеру.
- Список релеев обновляется подписанным манифестом из нескольких источников (HTTPS + IPFS), плюс локальные правки пользователя.
- Tor `fallback`: каждое соединение сначала пробуется напрямую, при
  ошибке — через SOCKS5 Tor.
- Tor `always`: все соединения только через SOCKS5 Tor; если Tor
  недоступен — ошибка, прямого соединения нет (fail-closed).
- Tor — встроенный `arti-client` в процессе `oc-tui`: bootstrap
  (10–60 c первый раз, дальше кэш директорий в каталоге состояния),
  SOCKS5 на 127.0.0.1:9050 поверх `TorClient::connect`.
- Мосты (obfs4 ×2, webtunnel ×2) — опциональный пункт настроек
  «Tor bridges»: для них нужны pluggable-transport бинарники
  `obfs4proxy` и `webtunnel-client` (ограничение архитектуры Tor/arti).
  Мосты в публичном репозитории блокируются быстрее — при смерти
  заменять в коде (`oc-tui/src/tor.rs`); механизма ротации пока нет.

### 9.3 Камуфляж
- Только стандартный TLS 1.3 (rustls), реальный SNI, обычные WebSocket-фреймы.
- Никаких самописных заголовков до шифрования.
- Уважать лимиты релеев (rate limit, ephemeral events, TTL), иначе бан = поведенческая деанонимизация.
- Паддинг + рандомизация `created_at` уже скрывают размеры и время; cover-трафик — опция.
- Никакой телеметрии и сетевой аналитики.

## 10. Релеи

### 10.1 Протокол релея
Минимальный публичный API (WebSocket, JSON):
```
WS   /ws?mailbox=<hex>&since=<ts>          // один ящик, совместимость
WS   /ws?mailboxes=<hex>,<hex>,...&since=<ts>
     client -> {"type":"publish","event":{...}}   // можно и без mailbox
     client -> {"type":"subscribe","mailboxes":["<hex>",...],"since":<ts>}
     client -> {"type":"ping"}
     relay  -> {"type":"event","event":{...}}
     relay  -> {"type":"published"} | {"type":"subscribed"} | {"type":"pong"}
             | {"type":"error","message":"..."}

POST /publish   { mailbox, created_at, expires_at, payload_b64 }   // совместимость
GET  /health
```
- Основной путь клиента — один WebSocket: мультиплексированная подписка,
  публикация и ping.
- `subscribe` добавляет ящики к открытому соединению и проигрывает
  сохранённые события новее `since`; лимит — 4096 ящиков на соединение.
- `POST /publish` оставлен для простых интеграций и отладки.
- Релей не требует аккаунта и не хранит IP в логах (по умолчанию access-log отсутствует).
- Хранит только `mailbox`, `created_at`, `expires_at`, `payload` (шифротекст).
- TTL по умолчанию 7 дней, лимит на ящик — 100 сообщений, payload — 64 KiB.
- Никакой валидации содержимого (оно непрозрачно).
- Опционально: `.onion`-адрес через Tor onion service.

### 10.2 Пул по умолчанию
- Курируемый список в репозитории (`relays/default.json`).
- Удалённые обновления — подписанный манифест:
  `{ version, issued_at, expires_at, relays, signature }`.
  Подпись Ed25519 покрывает `"openchat/relay-manifest/v1"` и канонический
  JSON без поля `signature`. Клиент принимает манифест только при валидной
  подписи проекта, неистёкшем `expires_at` и валидных URL; локальные
  релеи при ошибке источника не удаляются.
- Сейчас в списке публичные MQTT-брокеры (HiveMQ, EMQX, Eclipse Mosquitto
  test): они предназначены для тестирования, могут быть недоступны, и
  пул автоматически исключает мёртвые. Собственные `oc-relay` добавятся
  после первого развёртывания (см. `relays/README.md`).
- В репозитории — `oc-relay`, чтобы сообщество/любой человек мог поднять свой.
- Пользователь может добавить любой совместимый релей (`oc relays --add`);
  `oc relays --check` проверяет доступность.
- Пул хранит счётчик последовательных ошибок: релей с двумя ошибками
  временно исключается из fan-out, но остаётся в подписках; успешный
  health-check возвращает его в пул.

### 10.3 Этикет
Клиент обязан: соблюдать rate limit, не спамить cover-трафиком, ставить TTL, не публиковать мусор. Нарушение = бан релея = потеря устойчивости.

## 11. Клиент

### 11.1 Стек
- Ядро: Rust, `#![forbid(unsafe_code)]`.
- UI: CLI (`oc`: одноразовые команды + интерактивный `chat`) и TUI (`oc-tui`, ratatui) — одна программа на пользователя: TUI содержит всё (создание identity, пароль, invite, чат), `--cli` внутри неё открывает CLI-режим. GUI-версия (egui) удалена по решению пользователя: TUI понравился больше.
- Сборка под glibc и musl одной командой с `--target` (см. README §Сборка); musl-бинарник статический и работает и на glibc-системах.
- Мобильные позже: `uniffi` → Kotlin/Swift.
- Крипто: `ed25519-dalek`, `x25519-dalek`, `ml-kem`, `chacha20poly1305`, `hkdf`, `sha2`, `blake2`.
- Транспорт: `tokio`, `tokio-tungstenite`, `rustls` (+ `arti-client` для Tor).
- Tor: `arti-client` (rustls, статическая сборка для musl).
- Хранилище: зашифрованный файл состояния (XChaCha20-Poly1305); OS keyring и SQLCipher — позже.

### 11.4 Состояние клиента (P3)
Файл `state.enc` (права `0600`):
```
magic(8) || salt(16) || nonce(24) || XChaCha20-Poly1305(JSON state)
```
- Ключ: `Argon2id(passphrase, salt, m=19456, t=2, p=1)`.
- Пароль: `OPENCHAT_PASSPHRASE` или интерактивный ввод (`rpassword`).
- В состоянии: identity, текущие и до двух retired prekeys, подписанный
  bundle, контакты, ratchet snapshots, mailbox roots, safety numbers,
  outbox, последние 4096 `msg_id`/ACK и per-mailbox курсоры.
- Ротация prekey автоматическая при открытии состояния (раз в 7 дней) или
  вручную (`oc rotate`); существующие ratchet-сессии не затрагиваются.
- Запись атомарная: `state.enc.tmp` → `rename`.
- OS keyring — следующий шаг; текущий режим использует пароль и
  зашифрованный файл.
- Исходящая очередь (`outbox`) входит в зашифрованное состояние:
  `{ msg_id, peer_id, mailbox, payload, created_at, expires_at, attempts,
  next_attempt_at }`. Запись добавляется **до** первой публикации, поэтому
  сбой релея не теряет кадр, уже продвинувший ratchet. Ретраи идут с
  экспоненциальным backoff (5 s … 300 s) и ограничены TTL события.
- Успешно расшифрованный текст подтверждается кадром `ACK`; отправитель
  хранит последние 4096 подтверждений. ACK также проходит через outbox.
- Для каждого ящика хранится курсор `last_created_at`. Так как у
  `subscribe` один общий `since`, клиент подписывается от минимального
  курсора; при перезапуске это не перечитывает весь store. `since`
  эксклюзивен, поэтому возобновление идёт с `last_created_at - 1`.
- Каждый релейный поток оборачивается в независимый reconnect-loop с
  backoff 250 ms … 30 s. Ошибка или закрытие одного релея не завершает
  общий поток и не прерывает `listen`.

### 11.5 CLI (`oc`)

- Одноразовые команды: `init`, `invite`, `add`, `send`, `listen`,
  `contacts`, `flush`, `outbox`, `rotate`, `relays`.
- `chat [PEER]` — интерактивный режим в одном процессе: входящие события
  опрашиваются с паузой 1 c, ввод читается построчно (тайм-авт 1 c).
  Команды внутри: `/help`, `/peer <prefix>`, `/quit` (алиас `/exit`).
  Текст без `/` отправляется выбранному контакту обычным путём через outbox.
- История открытым текстом не хранится (в состоянии её нет по дизайну):
  сообщения печатаются при получении или при replay с релея.

### 11.6 TUI (`oc-tui`)

- Бинарник `oc-tui` на ratatui + crossterm; в workspace входит, но не
  в `default-members` (собирается по требованию).
- Экран входа в двух режимах (переключение **F2**):
  - *Unlock*: каталог состояния + пароль, Enter — открыть.
  - *Create*: каталог + пароль + повтор; **F3** генерирует сильный
    пароль (`word-word-word-word-1234`, CSPRNG). Создаёт identity и
    зашифрованное состояние прямо в TUI, релеи — из встроенного списка.
- После входа: контакты слева (↑↓, Enter), переписка по центру
  (автопрокрутка, safety number в заголовке), ввод снизу.
  Команды в вводе: `/invite` (короткая ссылка + полная в отдельной панели;
  **C** — скопировать короткую в буфер через OSC 52, Esc — закрыть),
  `/add <invite>` (или вставка `openchat://…`), `/contacts`,
  `/flush`, `/help`, `/quit`; `Ctrl+C` — выход. В шапке — только
  короткий peer id, полная ссылка живёт в панели invite.
- `oc-tui --cli …` — тот же CLI, что и `oc` (общий код в библиотеке
  `oc-cli`), без переключения бинарника.
- Протокол и состояние общие с CLI (`oc-client`): фоновый воркер владеет
  `Client` и пулом, UI общается с ним каналами. История — только
  на время сессии, как и в CLI.
- `/settings` — меню настроек (сохраняются в `<home>/settings.json`,
  не содержит секретов): Tor-режим (`off`/`fallback`/`always`),
  Tor-мосты вкл/выкл (нужны PT-бинарники), fanout публикаций (1–5),
  показывать ли invite при старте, WebRTC direct delivery вкл/выкл
  (по умолчанию выкл.). Смена настроек перезапускает воркер.
- Windows: тот же `oc-tui` собирается в exe
  (`--target x86_64-pc-windows-msvc` на Windows-машине) и открывает
  тот же TUI.

## 13. Инженерные правила

- Никакой самодельной криптографии: только проверенные примитивы; протокол — по опубликованным спецификациям (X3DH, Double Ratchet).
- Все секреты — `zeroize` на drop.
- Постоянное сравнение ключей — только `subtle`.
- Каждый примитив и формат — с тест-векторами.
- Внешний аудит до релиза; версия 1.0 без аудита не выпускается.
- Никаких секретов и IP в логах; логи по умолчанию выключены.
- Обновления подписанные, минимум два независимых источника.
